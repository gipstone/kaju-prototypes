Zielarchitektur

Drei Netzwelten statt einer direkten Verbindung: KNP-intern, eine neutrale Exchange-/Relay-Zone und die als potenziell kompromittierbar behandelte Compute-/Agent-Zone.

Sicherheitsidee: Beide Seiten initiieren ausschließlich ausgehende Verbindungen zum Relay. Selbst wenn ein Agent vollständig kompromittiert wäre, existiert technisch keine Route zum KNP-Server. Rückgaben werden auf dem KNP-Gateway als Daten behandelt, nie automatisch ausgeführt.

Warum die Netztrennung wichtiger ist als „der Agent darf das nicht“

Agenten können Code ausführen und externe Inhalte verarbeiten. Deshalb wird die Compute-Seite wie ein potenziell kompromittierter Rechner behandelt.

Angriffsweg

Prompt Injection / fremder Code

Ein Plan, Repository, Paket oder Webinhalt könnte versuchen, den Agenten zu unerwünschten Aktionen zu bewegen. Sicherheitsannahme: Das kann irgendwann gelingen.

Primäre Abwehr

Keine Route + keine Secrets

Ohne Layer-3/4-Route, internes DNS und KNP-Credentials kann der Agent weder Server scannen noch SMB/SQL/Access/SSH im KNP-Netz ansprechen.

Sekundäre Abwehr

Schema + Quarantäne

Relay und Gateway akzeptieren nur definierte JSON-/Dateiformate, Größen und MIME-Typen. Rückgabedateien werden nicht automatisch ausgeführt oder geöffnet.

Empfohlene Firewall-/Netzregeln
VerbindungRegel

MVP – kleinster wirklich wertvoller End-to-End-Schnitt

Der MVP soll die neue Architektur beweisen und im Büro bereits Nutzen schaffen, ohne die schwierigsten Alt-/Fachsysteme sofort automatisieren zu müssen.

1

Task + Relay

Interner Task wird pseudonymisiert, über Relay an Compute übergeben, bearbeitet und sicher zurückgeführt.

2

DIN-/Wiki-Recherche

Compute stellt Fachfrage; lokaler Research Agent liefert belegtes Evidence Packet mit Fundstelle.

3

Einfache Bauphysik

Ein klar abgegrenztes validiertes Modul, z. B. Bauteil/U-Wert bzw. strukturierte Hüllflächenprüfung, wird aus Tool Registry ausgeführt.

4

KNP-Report

Ergebnis wird als nachvollziehbarer HTML/PDF-Bericht und optional KNP-Schriftstück aus einer internen Vorlage erzeugt.

Was bewusst noch nicht in MVP 1 gehört
vollautomatische E-Mail-Ablagevollständige Access-Schreibintegrationuniverselle Planinterpretationvollständiger GEG-NachweisDIN V 18599 komplettproduktiver FEM-Wärmebrückenkernautonomer Dokumentversand

Umsetzungsstrategie: Was muss intern gebaut werden, was kann Cloud-Code bauen?

Die interne Zone ist der Engpass, weil dort Zugriff auf echte Daten und Systeme manuell eingerichtet und geprüft werden muss. Deshalb dort möglichst kleine, stabile Dienste bauen.

BausteinKNP-sichere ZoneCloud-/Compute-Zone
Netzwerk / IdentitätFirewall, Gateway, lokale Service-Accounts, ACLs, mTLS-Zertifikateisolierter Host/Container, Relay-Credential, Egress-Allowlist
Taskingechte Projektzuordnung, Pseudonymisierung, Freigabeneutrale Ticket-DB, Workspace, Agent-Orchestrierung
RechercheKNP-Wiki, Normen/Literatur, lokale Retrieval-Pipeline, PII-FilterResearch Request formulieren und Evidence verwenden
DokumenteKNP-Vorlagen, echte Projektdaten, finale DOCX/PPTX/PDF-Erzeugungpseudonymisierte Gliederung, Tabellen-/Grafikdaten, Textentwürfe
Rechenmodulefachliche Validierung/Freigabe und ggf. lizenzierte ReferenzsoftwareEntwicklung, Tests, Benchmarks, Ausführung freigegebener Module
E-Mail / Accessvollständig intern: Human Gate + Write Brokerkein Zugriff
ReportingProjektidentität ergänzen, final ablegentechnischen Report aus pseudonymisierten Inputs erzeugen
Entwicklungsprinzip: Cloud-Code kann den Großteil der Software entwickeln. Für interne Komponenten liefert es Code/Tests als Artefakt über das Relay; ein Mensch bzw. ein interner CI-/Deployment-Prozess prüft und installiert ihn. Der Agent bekommt dafür niemals direkten SSH-/Git-/Filesystem-Zugriff auf den KNP-Produktivserver.

Fachliche Qualität: Agent darf lernen, aber nicht selbst freigeben

Neue Tools können automatisch entwickelt werden; produktive Ingenieurergebnisse bleiben an KNP-validierte Versionen gebunden.

StatusBedeutungProduktiv
ExperimentalAgenten-Prototyp, noch nicht fachlich abgesichert.Nein
Benchmarkedautomatische Referenz- und Regressionstests bestanden.Nein
KNP-validiertgegen Referenzsoftware/analytische Fälle geprüft; Gültigkeitsbereich dokumentiert; menschlich freigegeben.Ja
Wärmebrücken/FEM: Ein neuer Kern wird erst nach Gegenrechnung gegen etablierte Software, analytische Benchmarkfälle, Netz-/Konvergenztests und festgelegte Toleranzen als produktiv markiert. Bis dahin muss jeder Report deutlich „nicht validiert“ zeigen.
