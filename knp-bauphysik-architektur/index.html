Leitprinzipien

Cloud-Fähigkeit und kontinuierliche Werkzeugentwicklung werden mit harten Datenschutz- und Qualitätsgrenzen kombiniert.

01 · Intern

Rohdaten bleiben intern

Kunden-, Projekt-, E-Mail-, Originalplan- und geschützte Fachinformationen verbleiben in der vertrauenswürdigen KNP-Zone.

02 · Grenze

Kein Direktzugriff

Compute-/Cloud-Agenten besitzen keine Route zu Originalprojekten oder zum zentralen Datenbestand.

03 · Adaptiv

System verbessert seine Werkzeuge

Der Agent lernt aus Aufgaben, erkennt Lücken und entwickelt neue Methoden und Tools – zunächst ausschließlich experimentell.

04 · Freigabe

Produktiv nur validiert

Belastbare Ergebnisse dürfen ausschließlich auf KNP-validierten Versionen und freigegebenen Berechnungsschritten beruhen.

Wichtig: „Selbstlernend“ bedeutet hier kein unkontrolliertes Online-Training des LLM. Gelernt werden Werkzeugwahl, Workflows, Benchmarks, Fehlerbilder und wiederverwendbare Rechenmethoden. Neue Logik gelangt nur über eine explizite Validierungs- und Freigabeschleuse in den produktiven Bestand.

Zielarchitektur

Projekt- und Wissensdaten liegen intern; die Compute-/Agent-Zone arbeitet ausschließlich mit freigegebenen Ticketpaketen und fachlichen Evidence-Paketen.

Normen, Fachbücher und Fachartikel

Lizenzierte oder urheberrechtlich geschützte Quellen werden nicht in die Cloud kopiert. Die lokale Wissensschicht beantwortet konkrete Fachfragen mit Provenienz.

Knowledge Vault

Geschützter Bestand

Originale und abgeleitete Markdown-/Bilddaten liegen ausschließlich intern und werden mit Quelle, Ausgabe, Rechten und zulässiger KI-Nutzung katalogisiert.

Research Agent

Lokale Recherche

Das lokale LLM erhält eine konkrete Fachfrage, recherchiert in den intern zulässigen Quellen und liefert eine belegte Antwort.

Evidence Packet

Cloud erhält nur Fachwissen

Weitergegeben werden konkrete Aussagen, Parameter und Fundstellen – nicht die vollständigen geschützten Dokumente.

Lizenz-Gate: Ob ein Dokument überhaupt automatisiert extrahiert, indexiert oder von einem lokalen LLM verarbeitet werden darf, wird pro Quelle als Rechte-Metadatum hinterlegt. Technische Isolation ersetzt keine erforderliche Lizenz.

Adaptiver / „selbstlernender“ Compute-Agent

Der Compute-Agent soll für jede Aufgabe die geeignetste vorhandene Werkzeugkette auswählen und systematisch erkennen, wann neue Fähigkeiten erforderlich sind.

1 · Aufgabe verstehenPhysik, Zielgrößen, Genauigkeit
→
2 · Tool Registry prüfenwelche freigegebenen Module passen?
→
3 · RechenplanMethoden + Randbedingungen
→
4 · Capability Gatealles validiert?
→
5 · Berechnungoder Entwicklungs-Task
Capability Memory

Erfahrungen werden wiederverwendet

Das System speichert, welche Tools für welche Problemklasse funktioniert haben, typische Fehlerbilder, Benchmarks, Laufzeiten und geeignete Modellierungsstrategien.

Gap Detection

Fehlende Fähigkeit erkennen

Reicht kein freigegebenes Werkzeug aus, wird die Aufgabe nicht stillschweigend improvisiert. Stattdessen erzeugt der Agent einen Tool-Development-/Validation-Task.

No Auto-Promotion

Keine Selbstfreigabe

Ein vom Agenten entwickeltes Tool darf sich niemals selbst auf „produktiv“ setzen. Die Freigabe bleibt ein kontrollierter KNP-Prozess.

Entscheidungslogik für eine Aufgabe
if all_required_steps.status == KNP_VALIDATED:
    run_production_calculation()
    assurance = "validated"
elif validated_fallback_exists:
    use_validated_fallback()
    assurance = "validated_with_limitations"
else:
    create_tool_development_task()
    optional_experimental_run()
    assurance = "UNVERIFIED"
    block_final_engineering_release()

Tool Registry, Validierung und Freigabegates

Jeder Rechenkern, jedes Skript und jeder fachlich relevante Berechnungsschritt hat Version, Status, Gültigkeitsbereich und dokumentierte Validierungsbasis.

StatusBedeutungProduktiver Nachweis
ExperimentalPrototyp oder neu entwickelte Methode; fachlich noch nicht ausreichend geprüft.Nein
BenchmarkedAutomatische Testfälle/Referenzfälle bestanden, aber noch keine formale KNP-Freigabe.Nein
KNP-validiertGegen Referenzsoftware, analytische Fälle und/oder belastbare Vergleichsdaten geprüft; Version und Anwendungsbereich freigegeben.Ja
DeprecatedAlte Version; reproduzierbar archiviert, für neue Berechnungen gesperrt.Nein
Referenzsoftware

Cross-Validation

Beispielsweise wird ein neuer Wärmebrückenkern gegen etablierte Software mit identischen Geometrien, Materialien und Randbedingungen gerechnet und die Abweichung bewertet.

Regression Suite

Freigabe bleibt reproduzierbar

Jede Änderung muss den gesamten Bestand definierter Referenzfälle erneut bestehen. Numerische Toleranzen werden explizit festgelegt.

Human Gate

KNP gibt Version frei

Ein Mensch prüft Validierungsreport, Grenzen und offene Abweichungen und setzt erst danach die konkrete Tool-Version auf KNP-validiert.

Aktueller Soll-Workflow

Vom Eingang einer Aufgabe bis zum fachlich freigabefähigen Ergebnis.

  1. Das lokale LLM analysiert interne Quellen und erzeugt einen internen Task.
  2. Das Gateway bildet daraus ein pseudonymisiertes Compute-Ticket.
  3. Der Compute-Agent analysiert die physikalische Problemklasse und prüft Tool Registry und Capability Memory.
  4. Fehlende normative/fachliche Informationen werden als Research Request an das lokale LLM zurückgegeben und als Evidence Packet beantwortet.
  5. Der Agent erstellt einen Rechenplan und prüft für jeden Schritt Status und Gültigkeitsbereich der vorgesehenen Tools.
  6. Sind alle ergebnisrelevanten Schritte KNP-validiert, wird produktiv gerechnet.
  7. Fehlt eine validierte Fähigkeit, wird ein Tool-Development-/Validation-Task erzeugt; optionale Ergebnisse bleiben ausdrücklich ungesichert.
  8. Neue oder geänderte Tools werden gegen Referenzsoftware, analytische Fälle und Regressionstests geprüft.
  9. Erst nach menschlicher KNP-Freigabe wird eine konkrete Version produktiv nutzbar.
  10. Der Rechenjob erzeugt Ergebnisdaten, Visualisierungen und einen reproduzierbaren technischen Report.
  11. Das interne System ordnet Ticket und Resultate wieder dem realen Projekt zu.
