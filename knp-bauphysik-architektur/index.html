Leitprinzipien

Cloud-Fähigkeit, Automation und kontinuierliche Werkzeugentwicklung werden mit harten Datenschutz-, Schreib- und Qualitätsgrenzen kombiniert.

01 · Intern

Rohdaten bleiben intern

Kunden-, Projekt-, E-Mail-, Originalplan- und geschützte Fachinformationen verbleiben in der vertrauenswürdigen KNP-Zone.

02 · Schreibgrenze

LLM schreibt nie direkt

Das lokale LLM darf lesen, analysieren und Vorschläge erzeugen. Produktive Änderungen erfolgen nur über fest programmierte Dienste.

03 · Adaptiv

System verbessert seine Werkzeuge

Der Agent erkennt Lücken und entwickelt neue Methoden und Tools – zunächst ausschließlich experimentell.

04 · Freigabe

Produktiv nur validiert

Belastbare Ergebnisse dürfen ausschließlich auf KNP-validierten Versionen und freigegebenen Berechnungsschritten beruhen.

Selbstlernend ≠ selbstfreigebend: Das System darf aus Aufgaben lernen und neue Tools entwickeln, aber weder neue Rechenlogik noch produktive Schreibaktionen selbstständig freigeben.

Zielarchitektur

Die Übersicht zeigt bewusst nur die wichtigsten Stationen. Grün bleibt vollständig intern; unterhalb der roten Grenze arbeitet die Compute-/Cloud-Welt nur mit pseudonymisierten Tickets und freigegebenem Fachwissen.

Leserichtung: oben beginnt die echte KNP-Welt. Links liegt der kontrollierte Schreibpfad mit Human Gate; rechts verlässt ausschließlich ein reduziertes Ticket die interne Zone. Unten arbeitet der Compute-Agent mit freigegebenen Rechentools und liefert Report und Ergebnisse wieder zurück.

Mail UI

Eigene interne Oberfläche

Inbox mit KI-Vorschlag, vorgeschlagenem Projekt, Zielordner, Dokumenttyp und Dateiname. Ein Klick bestätigt oder korrigiert die Ablage.

Human Gate

Schreiben erst nach Bestätigung

Der Mensch bestätigt den konkreten Zielzustand. Erst danach erhält der Write Broker einen eng definierten Auftrag.

Write Broker

Minimal privilegierter Dienst

Darf nur freigegebene Operationen: Maildatei kopieren/verschieben, Metadaten schreiben, Access-Datensatz anlegen/ändern und Audit-Eintrag erzeugen.

Beispiel einer bestätigten Ablageaktion

source_message_id: <mail-id>
approved_project_id: P-0241
actions:
  - store_email: /projekte/P-0241/05_Korrespondenz/...
  - store_attachments: true
  - access_link: P-0241
  - write_audit_record: true

Der Write Broker akzeptiert keine freien Shell-Befehle oder LLM-Prompts, sondern nur ein festes, validiertes Aktionsschema.

Normen, Fachbücher und Fachartikel

Lizenzierte oder urheberrechtlich geschützte Quellen werden nicht in die Cloud kopiert. Die lokale Wissensschicht beantwortet konkrete Fachfragen mit Provenienz.

Knowledge Vault

Geschützter Bestand

Originale und abgeleitete Markdown-/Bilddaten liegen intern und werden mit Quelle, Ausgabe, Rechten und zulässiger KI-Nutzung katalogisiert.

Research Agent

Lokale Recherche

Das lokale LLM recherchiert konkrete Fachfragen in zulässigen Quellen und liefert eine belegte Antwort.

Evidence Packet

Cloud erhält nur Fachwissen

Weitergegeben werden konkrete Aussagen, Parameter und Fundstellen – nicht die vollständigen geschützten Dokumente.

Lizenz-Gate: Ob ein Dokument automatisiert extrahiert, indexiert oder von einem lokalen LLM verarbeitet werden darf, wird pro Quelle als Rechte-Metadatum hinterlegt.

Capability Memory

Erfahrungen wiederverwenden

Geeignete Tools, Modellierungsstrategien, typische Fehlerbilder, Benchmarks und Laufzeiten werden strukturiert gespeichert.

Gap Detection

Fehlende Fähigkeit erkennen

Reicht kein freigegebenes Werkzeug aus, wird ein Tool-Development-/Validation-Task erzeugt.

No Auto-Promotion

Keine Selbstfreigabe

Ein vom Agenten entwickeltes Tool darf sich niemals selbst auf produktiv setzen.

Entscheidungslogik
if all_required_steps.status == KNP_VALIDATED:
    run_production_calculation()
    assurance = "validated"
elif validated_fallback_exists:
    use_validated_fallback()
    assurance = "validated_with_limitations"
else:
    create_tool_development_task()
    optional_experimental_run()
    assurance = "UNVERIFIED"
    block_final_engineering_release()

Tool Registry, Validierung und Freigabegates

Jeder Rechenkern, jedes Skript und jeder fachlich relevante Berechnungsschritt hat Version, Status, Gültigkeitsbereich und dokumentierte Validierungsbasis.

StatusBedeutungProduktiver Nachweis
ExperimentalPrototyp oder neue Methode; fachlich noch nicht ausreichend geprüft.Nein
BenchmarkedAutomatische Referenzfälle bestanden, aber noch keine formale KNP-Freigabe.Nein
KNP-validiertGegen Referenzsoftware, analytische Fälle und/oder belastbare Vergleichsdaten geprüft.Ja
DeprecatedAlte Version; reproduzierbar archiviert und für neue Berechnungen gesperrt.Nein
Referenzsoftware

Cross-Validation

Neue Kerne werden mit identischen Geometrien, Materialien und Randbedingungen gegen etablierte Software gerechnet.

Regression Suite

Freigabe bleibt reproduzierbar

Jede Änderung muss den gesamten Bestand definierter Referenzfälle innerhalb festgelegter Toleranzen bestehen.

Human Gate

KNP gibt Version frei

Erst ein menschlicher Review setzt die konkrete Tool-Version auf KNP-validiert.

Grundregel: Ein Bericht darf die Kennzeichnung „validiertes Ergebnis“ nur erhalten, wenn jeder fachlich ergebnisrelevante Schritt auf einer freigegebenen Version innerhalb ihres dokumentierten Gültigkeitsbereichs beruht.

Backup, Audit und Wiederherstellung

Automatisierung darf bestehende KNP-Daten nur verändern, wenn jede Änderung nachvollziehbar und die Daten unabhängig wiederherstellbar sind.

Audit Journal

Jede Änderung protokollieren

Transaktions-ID, Benutzer, Zeitpunkt, Projekt, Operation, betroffene Datensätze, Vorher-/Nachher-Werte, Zielpfad und Datei-Hash.

Snapshots

Regelmäßige Sicherungen

Access-Backend und relevante Projektmetadaten werden versioniert bzw. in ausreichend kurzen Intervallen gesichert.

Restore-Test

Backups müssen funktionieren

Wiederherstellung wird regelmäßig getestet; ein Backup gilt erst dann als belastbar, wenn ein Restore nachgewiesen wurde.

Aktueller Soll-Workflow

Vom Eingang einer Aufgabe bis zum fachlich freigabefähigen Ergebnis.

  1. Das lokale LLM analysiert interne Quellen und erzeugt einen internen Task.
  2. Produktive Schreibvorgänge werden als Vorschlag im Human-Gate UI angezeigt und erst nach Bestätigung durch den Write Broker ausgeführt.
  3. Für Berechnungen erzeugt das Sanitization Gateway ein pseudonymisiertes Compute-Ticket.
  4. Der Compute-Agent analysiert die physikalische Problemklasse und prüft Tool Registry und Capability Memory.
  5. Fehlende normative/fachliche Informationen werden als Research Request lokal beantwortet und als Evidence Packet zurückgegeben.
  6. Der Agent erstellt einen Rechenplan und prüft Status und Gültigkeitsbereich jedes vorgesehenen Tools.
  7. Sind alle ergebnisrelevanten Schritte KNP-validiert, wird produktiv gerechnet.
  8. Fehlt eine validierte Fähigkeit, wird ein Tool-Development-/Validation-Task erzeugt; optionale Ergebnisse bleiben ausdrücklich ungesichert.
  9. Neue oder geänderte Tools werden gegen Referenzsoftware, analytische Fälle und Regressionstests geprüft.
  10. Erst nach menschlicher KNP-Freigabe wird eine konkrete Version produktiv nutzbar.
  11. Der Rechenjob erzeugt Ergebnisdaten, Visualisierungen und einen reproduzierbaren technischen Report.
  12. Das interne System ordnet Ticket und Resultate wieder dem realen Projekt zu.
